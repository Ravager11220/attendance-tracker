Software Requirements Specification (SRS)

Ephemeral Biometric Attendance System (EBAS)

1. Introduction

1.1 Purpose

This document specifies the software requirements for the Ephemeral Biometric Attendance System (EBAS). It defines the functional, non-functional, and system interface requirements designed to mitigate attendance proxying in classroom environments using WebAuthn biometrics, short-lived server sessions, and edge network tunneling.

1.2 Scope

EBAS is a lightweight web application that enables instructors to collect verified student attendance in real time.

In-Scope: Public-key hardware attestation (WebAuthn), rolling session token validation, server-side duplicate suppression, and CSV data exports.

Out-of-Scope: Campus ERP grade synchronization, long-term student leave management, and native mobile client installations.

1.3 Definitions and Acronyms

SRS: Software Requirements Specification

WebAuthn: Web Authentication API (FIDO2 public-key cryptography standard)

Ephemeral Session: A backend state active only for a strict 1–2 minute execution window.

Credential ID: A unique cryptographic handle generated by a device's local Secure Enclave.

WAL: Write-Ahead Logging (SQLite concurrency mode).

2. Overall Description

2.1 Product Perspective

EBAS is a standalone backend system deployed on instructor hardware and exposed securely to client browsers via an encrypted Cloudflare reverse tunnel. It operates independently of campus database infrastructure to eliminate deployment friction.

2.2 User Classes and Characteristics

Instructor (Admin): Initiates session windows, displays dynamic QR codes, monitors live check-ins, and exports finalized attendance logs.

Student (User): Scans projector QR codes and completes OS-level biometric verification via a standard mobile web browser.

2.3 Operating Environment

Backend Framework: Python 3.10+, FastAPI asynchronous framework.

Database Engine: SQLite 3.x configured in WAL mode for high-concurrency access.

Network Tunnel: Cloudflare Tunnel (cloudflared) providing outbound edge HTTPS routing.

Client Environment: Modern WebAuthn-enabled mobile browser (Chrome, Safari, Firefox).

3. External Interface Requirements

3.1 User Interfaces

Instructor Dashboard: Web interface featuring active session control timers, live check-in counters, dynamic QR streaming, and a one-click CSV export trigger.

Student Check-In View: Minimalist web interface containing input fields for roll_number and a direct trigger for device-level biometric authentication.

3.2 Software Interfaces

WebAuthn API: Browser-native interface communicating directly with client OS Secure Enclaves (Touch ID, Face ID, Android Biometrics).

SQLite Relational Store: Embedded database managing session-scoped roll numbers and credential hashes.

4. System Features & Functional Requirements

FR-1: Ephemeral Session Management

FR-1.1: The system shall allow the instructor to initialize a named attendance session.

FR-1.2: The backend shall automatically stop accepting incoming submissions after a configurable timeout (default: 120 seconds).

FR-2: Cryptographic Attendance Verification

FR-2.1: Upon receiving a student submission, the system shall execute a WebAuthn challenge/response verification.

FR-2.2: The system shall extract the returning credential_id and bind it to the submitted roll_number.

FR-3: Anti-Proxy & Session Locking

FR-3.1: The system shall reject any submission attempt for a roll_number that has already logged attendance within the current active session.

FR-3.2: The system shall reject any submission attempt containing a credential_id that has already been recorded within the current active session.

FR-4: Data Archival

FR-4.1: The system shall expose an endpoint to aggregate and stream session records into a downloadable standard CSV format containing Timestamp, Roll Number, Session Name, and Credential Hash.

5. Non-Functional Requirements

5.1 Security Requirements

SR-1 (Zero Biometric Leakage): The system shall never transmit or store raw biological fingerprint or facial scan data. All biometric checks must remain entirely localized to the user device's hardware Secure Enclave.

SR-2 (Transport Layer Security): All traffic between client web browsers and the local backend server must be encrypted in transit via HTTPS provided by the edge tunnel.

5.2 Performance & Concurrency Requirements

PR-1: The backend API shall process up to 100 concurrent HTTP POST check-in requests per second without raising database lock errors or dropping client connections.

PR-2: The WebAuthn verification endpoint response time shall not exceed 500 milliseconds under normal classroom load.

5.3 Reliability & Fault Tolerance

RR-1: If an invalid payload or corrupted cryptographic signature is transmitted, the server must fail gracefully, returning a structured 400 Bad Request JSON error without breaking active thread execution.
