Software Requirements Specification (SRS)Ephemeral Biometric Attendance System (EBAS)1. Introduction1.1 PurposeThis document specifies the software requirements for the Ephemeral Biometric Attendance System (EBAS). It defines the functional, non-functional, and interface requirements designed to eliminate attendance proxying in classroom environments using WebAuthn biometrics, short-lived server sessions, and edge network tunneling.1.2 ScopeEBAS is a lightweight web application that allows instructors to collect verified student attendance.In-Scope: Public-key hardware registration (WebAuthn), rolling session token validation, backend session locking, and CSV data exports.Out-of-Scope: Campus ERP grade integrations, long-term leave management, and native mobile client applications.1.3 Definitions and AcronymsSRS: Software Requirements SpecificationWebAuthn: Web Authentication API (FIDO2 public-key cryptography standard)Ephemeral Session: A backend state active only for a strict 1–2 minute window.Credential ID: A unique cryptographic handle generated by a device's secure enclave.2. Overall Description2.1 Product PerspectiveEBAS is a standalone backend system deployed on local instructor hardware and exposed securely to client devices via a Cloudflare reverse tunnel. It operates independent of institutional database installations.2.2 User Classes and CharacteristicsInstructor (Admin): Initiates session windows, displays dynamic QR codes, and exports finalized attendance sheets.Student (User): Scans QR codes and completes biometric hardware prompts via a mobile web browser.2.3 Operating EnvironmentBackend Server: Python 3.10+, FastAPI framework, SQLite relational database.Network Infrastructure: Cloudflare Tunnel (cloudflared) providing outbound HTTPS edge routing.Client Environment: Modern web browser (Chrome, Safari, Firefox) with WebAuthn JavaScript API enabled.3. External Interface Requirements3.1 User InterfacesInstructor View: Minimalist dashboard showing active session timer, live attendance count, dynamic QR stream, and an "Export CSV" button.Student View: Simple form requiring input for roll_number and a button to trigger OS-level biometric verification.3.2 Software Interfaces   WebAuthn API: Browser-native interface used to communicate with device Secure Enclaves (Touch ID / Face ID / Android Biometrics).SQLite Database: Local persistent store operating in Write-Ahead Logging (WAL) mode for concurrent writes.4. System Features & Functional RequirementsFR-1: Ephemeral Session ManagementFR-1.1: The system shall allow the instructor to initialize a named attendance session.FR-1.2: The backend shall automatically terminate accepting submissions after a configurable timeout (default: 120 seconds).FR-2: Cryptographic Attendance VerificationFR-2.1: Upon receiving a student submission, the system shall execute a WebAuthn challenge/response verification.FR-2.2: The system shall capture the returning credential_id and bind it to the submitted roll_number.FR-3: Anti-Proxy & Session LockingFR-3.1: The system shall reject any submission attempt for a roll_number that has already logged attendance in the current active session.FR-3.2: The system shall reject any submission attempt containing a credential_id that has already been recorded in the active session.FR-4: Data ArchivalFR-4.1: The system shall provide a REST endpoint to compile session records into a standard CSV format (containing Timestamp, Roll Number, Session Name, and Credential Hash).5. Non-Functional Requirements5.1 Security RequirementsSR-1 (Zero Biometric Leakage): The system shall never receive, transmit, or store raw biological fingerprint or face scan data. All biometric verification must remain localized to the user device's Secure Enclave.SR-2 (Transport Encryption): All traffic between client browsers and the local server must be encrypted in transit via HTTPS provided by the edge tunnel.5.2 Performance & Concurrency RequirementsPR-1: The backend API shall handle up to 100 concurrent HTTP POST check-in requests per second without raising database lock errors or dropping connections.PR-2: The WebAuthn verification endpoint response time shall not exceed 500 milliseconds under normal classroom load.5.3 Reliability & AvailabilityRR-1: If an invalid payload or corrupted key signature is transmitted, the server must fail gracefully, returning a structured 400 Bad Request JSON error without breaking the running session thread.6.
